# Lizhi Image2.5 Visual PPT

Create presentation decks whose real slide design is generated by GPT Image 2.6 Sunburst. The PPTX is the delivery container: each slide contains one full-bleed generated image rather than native PPT text layout.

## Core Promise

- Preserve the user's required slide content unless they explicitly allow reduction or rewriting.
- Before generating images, transform raw material into a standardized high-density slide-content blueprint. Strong visual output depends on strong page-level information architecture, not color alone.
- Default to a human confirmation gate after the content blueprint is ready. Do not spend image-generation time or credits until the requester approves the blueprint, unless they explicitly asked to skip confirmation and generate directly.
- Generate every slide image with the selected GPT Image backend first. Do not imitate the visual design with Python, HTML screenshots, or PPT-native text boxes.
- Package the generated images into a PPTX with one full-slide image per slide.
- Keep styles and project content separate. A source document may be a whitepaper, speech, report, or proposal; that does not determine the visual style.
- Do not inherit names, logos, examples, or proprietary copy from previous decks.

## Model Backend (quality first)

The skill name retains `image25` by request; the current default backend is GPT Image 2.6 Sunburst. GPT Image 2.5 is supported only when explicitly selected.

- Default model: `gpt-image-2.6-sunburst`; `gpt-image-2.6-flare` is an explicit alternative.
- Prefer a host image tool when its metadata confirms the selected model. A tool named `image_gen` alone does not prove its model version; do not invent an unsupported model parameter.
- If the host cannot confirm the selected model, use the bundled API helper with an existing authorized `OPENAI_API_KEY`. Never silently downgrade. If neither route is available, deliver the blueprint and prompts and explain the missing backend.
- API helper, credentials, dimensions, and official sources: `references/image25-backend.md`.

## Two Independent Layers

Treat every deck as two separate design problems:

1. **Content blueprint** — what each page must communicate, how its evidence is grouped, what the audience should remember, and what layout can carry it.
2. **Visual style** — palette, mood, materials, typography, illustration language, and decorative system.

Do not use a style preset to compensate for weak content structure. Build the content blueprint first, then apply a selected style.

## Phase 1: Standardize the Content

Read `references/content-blueprint.md` before planning slides.

1. Extract the source's central thesis, audience, purpose, and available evidence.
2. Build a narrative arc rather than splitting text by length. Each page should advance one step in the argument.
3. Assign one dominant question or conclusion to each slide.
4. Group supporting material into two to five visualizable modules such as definitions, comparisons, data cards, timelines, pyramids, matrices, processes, cases, or quotes.
5. For every slide, state its page mission, content modules, takeaway, layout plan, visual elements, exact required copy, and constraints.
6. Save the result as `<project>/lizhi_image25_visual_ppt/content-blueprint.md` using the reference template.
7. Check the complete arc for repetition, missing transitions, unsupported claims, and deliberate callbacks before generating any slide image.
8. Present the blueprint for confirmation, including its file path and a concise summary of the slide count, narrative arc, page titles, major modules, and proposed layouts.
9. Stop before image generation and wait for explicit approval such as “确认生成”, “可以出图”, or an equivalent instruction.

If the source already arrives in this format, validate and reuse it instead of rewriting it. Data sources are not required on every slide, but factual claims must never be invented; preserve supplied sources when accuracy or external use matters.

## Content Approval Gate

The default workflow has a deliberate checkpoint because revising Markdown is fast, while regenerating many slide images is slow and consumes credits.

Before calling GPT Image 2.6 Sunburst:

1. Deliver or link the completed `content-blueprint.md`.
2. Ask the requester to confirm:
   - slide count and overall narrative
   - each page's title and central thesis
   - required content modules and omitted material
   - proposed page layouts and visual priorities
   - exact copy, facts, assets, and constraints
3. If revisions are requested, update the blueprint and present it again.
4. Begin image generation only after explicit approval.

Skip this checkpoint only when the requester clearly says “直接生成”, “无需确认”, “不要停下来问”, or equivalent language. General urgency alone does not imply permission to skip it.

## Style Selection

1. Read `references/style-catalog.md` to see the installed style presets.
2. If the user names an installed style, use it.
3. If the user does not specify a style, use the catalog's default preset.
4. If the user supplies a reference image, inspect it and translate its reusable visual traits into the slide prompts. Do not copy its brand-specific content.
5. If the user requests a style that is not installed and gives no reference, explain that only the installed presets are available and ask for a reference or permission to design a new preset.
6. Read only the selected preset file before writing slide prompts.

Current built-in state: `blue-white` is the default; `workbuddy-white-green` is also installed. “Whitepaper” may describe source content, but it is not the preset name.

## When Starting

1. Read the source material.
2. Create or validate the standardized content blueprint using Phase 1.
3. Present the blueprint and wait for explicit content approval, unless confirmation was explicitly waived.
4. Resolve the visual style using the selection rules above.
5. Ask a clarification if source content is missing or contradictory, a factual gap would require invention, or the requested style cannot be resolved.
6. Generate slide images only after the approval gate has passed.

## Slide Generation Workflow

Read `references/image25-backend.md` before generating. Generate one slide at a time with a verified GPT Image backend. Save each exact prompt and a generation record (requested model, backend, returned model if available, dimensions, filename) alongside the pages. Never infer the actual model from a prompt alone.

Use this prompt structure:

```text
Create a complete finished 16:9 presentation slide image.

SELECTED STYLE:
[Insert the selected preset guidance from references/styles/<preset>.md, or the reusable traits extracted from the user's reference image.]

PAGE MISSION:
[State what this slide must make the audience understand, feel, or remember.]

CONTENT TO PRESERVE EXACTLY:
[Paste the slide title, module headings, key copy, labels, numbers, and quotes from the content blueprint. Do not omit required points.]

LAYOUT:
[Describe the information architecture: title area, cards, diagram, timeline, table, side illustration, footer/source strip.]

VISUAL ELEMENTS:
[Specify icons, 3D objects, dashboard fragments, abstract data flows, maps, people/agent scenes, or other domain-relevant elements.]

CONSTRAINTS:
- The output is one complete slide image, not a mockup inside a frame.
- Follow the selected style consistently across the whole deck.
- No invented logo, no project-specific branding, no irrelevant decoration.
- Chinese text must be clear and professional.
```

### Text Handling

Image generation can distort long Chinese text. Protect important wording by putting required copy in the clearly labeled `CONTENT TO PRESERVE EXACTLY` block, then inspect the output.

If a slide drops or garbles important text:

1. Regenerate with fewer visual distractions around the affected text.
2. Increase local contrast and request larger text zones.
3. If the page remains too dense, ask whether content may be split. Do not split or shorten it without permission.

## File Organization

Use a project output folder such as:

```text
<project>/lizhi_image25_visual_ppt/
├── content-blueprint.md
├── pages/
│   ├── P01-cover.png
│   ├── P02-topic.png
│   └── ...
└── output/
    └── deck-name.pptx
```

Prefer stable filenames with page numbers so packaging preserves order.

## Build the PPTX

After all slide images are saved, run the bundled script:

```bash
node <skill-dir>/scripts/build_fullslide_deck.mjs \
  --images-dir <project>/lizhi_image25_visual_ppt/pages \
  --out <project>/lizhi_image25_visual_ppt/output/deck-name.pptx
```

The script creates a 16:9 deck and places each image full-bleed on its own slide. It does not add text boxes, shapes, speaker notes, or branding.

If `pptxgenjs` is unavailable in the active Node runtime, use the Codex workspace dependency runtime or install the package in a local scratch workspace. Keep the actual slide artwork as GPT Image 2.6 Sunburst-generated PNG/JPG files.

## Adding Future Styles

When the user asks to add a reusable visual style:

1. Create `references/styles/<style-id>.md` with palette, mood, layout patterns, visual ingredients, typography guidance, and avoid rules.
2. Add the style to `references/style-catalog.md` with a clear trigger description.
3. Change the default only when the user explicitly requests it.
4. Add or update a test prompt that selects the new style.

Do not mix multiple style definitions into the main workflow; keeping presets separate makes style choice explicit and scalable.

## QA Checklist

- The generation backend and requested model are recorded; unverified host versions are not labeled as confirmed model versions.
- Inspect every image for text, numbers, logos, and aspect ratio before packaging.
- The number of page images equals the requested slide count.
- A complete `content-blueprint.md` exists before image generation.
- Explicit blueprint approval was received, or the requester explicitly waived confirmation.
- Every slide has one dominant thesis and two to five coherent supporting modules.
- The deck has a deliberate narrative arc, transitions, and callbacks instead of disconnected pages.
- The PPTX contains the same number of slides.
- Every slide image fills the page edge to edge.
- The selected style is consistent across cover and inner pages.
- Content type has not been confused with visual style.
- Mandatory content has not been silently removed.
- No previous-project names, logos, or copy leaked into the deck.
- Any user-supplied logo or reference image was used only as requested.
